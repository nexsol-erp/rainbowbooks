Rainbow Books coir handicrafts store

A Spring Boot and React storefront for a five-piece catalogue of handwoven coir bird houses — guest and registered checkout, offline payment capture, persistent carts, and a full admin back office. Architecture

One repository, three containers, one database. The backend follows clean architecture: the domain layer knows nothing about JPA, HTTP, or SMTP, and every outward dependency enters through an interface the domain itself owns.

Backend layering

com.karvya.store.domain
Entities, value objects (Money, OrderNumber, Slug, Email), domain exceptions, state-transition rules, and repository interfaces. No Spring annotations — unit-testable with plain JUnit.
com.karvya.store.application
Use-case services owning the transaction boundary — PlaceOrderService, CartMergeService, CatalogQueryService, OrderAdminService, PasswordResetService. Command and result records, plus mappers.
com.karvya.store.infrastructure
Adapters implementing the domain's ports — Spring Data JPA repositories, LocalFileSystemStorage, SmtpMailSender, Flyway config, Spring Security wiring, rate limiters, the outbox worker.
com.karvya.store.web
Versioned REST controllers under /api/v1, request/response DTOs with Bean Validation, and a @RestControllerAdvice mapping domain exceptions to RFC 7807 problem responses. No entity ever crosses the wire.

Decisions worth stating up front

  • Sessions, not JWTs, for both audiences. Customers and administrators authenticate into server sessions held in an HttpOnly, Secure, SameSite=Lax cookie, persisted through Spring Session JDBC. Sessions survive a restart, and disabling an account or changing a password invalidates them immediately — a property bearer tokens cannot offer without a revocation list.
  • Two cart implementations behind one interface. Visitors keep a cart in localStorage; logged-in customers get a database cart. On login, CartMergeService combines them — duplicate products sum, and every line is capped at available stock rather than silently overselling.
  • The browser's totals are never authoritative. Cart contents are posted as product ids and quantities only. The server re-reads price, active status, and stock, recomputes the subtotal, delivery charge, and total, and rejects the checkout if anything moved.
  • Stock is protected by pessimistic row locks. The order transaction selects each product FOR UPDATE in ascending id order — the consistent ordering is what prevents deadlock between concurrent checkouts — while a version column guards admin edits against lost updates. This choice is documented in the README as the brief requires.
  • Cancellation restocks exactly once. A stock_restored_at timestamp on the order makes the restore idempotent: the transition re-reads the row under lock, and a second cancellation is a no-op rather than a double credit.
  • Order items are immutable snapshots. Name, SKU, unit price, quantity, and line total are copied onto the line at purchase. The product foreign key is nullable and set null on archive, so history survives catalogue changes.
  • Email cannot fail an order. The order commits first; notifications are rows in email_notification that a scheduled worker claims, sends, and retries with bounded exponential backoff — no busy polling, no long-held locks.
  • Images are files, not blobs. A StorageService port with a filesystem adapter today and S3 later. The database stores metadata and a stable relative key.
  • Payments have a seam but no implementation. A PaymentInitiator interface exists with only the offline implementation registered; phase two adds a gateway adapter without touching the order flow.

Database model

Eighteen tables created by V1__schema.sql. Money is NUMERIC(10,2) — never floating point. Timestamps are TIMESTAMPTZ. Every business table carries created_at and updated_at; every table a human acts on also carries updated_by. The orders table is customer_order, since order is reserved in SQL.

Indexes that earn their place

Unique on app_user(email_normalized), product(sku), product(slug), customer_order(order_number), cart_item(cart_id, product_id). Composite on product(status, category_id) and product(status, featured) for the catalogue, customer_order(status, placed_at DESC) for the admin list, customer_order(user_id, placed_at DESC) for order history, and a partial index on email_notification(next_attempt_at) WHERE status = 'PENDING' so the outbox worker touches only what it needs.

Order numbers

Format KV-260828-7QK4 — prefix, date, and four random base-32 characters from a secure random source. The date keeps it human and sortable; the random suffix keeps it non-guessable, so knowing one order number tells you nothing about another. Short enough to read aloud, which matters when payment gets settled over WhatsApp.

The guest confirmation page is guarded separately by an opaque token hashed into access_token_hash, so the order number alone is not enough to view an order.

Security model

Three audiences share one filter chain with different authorities. Every rule below is enforced server-side; the frontend mirrors some of them for usability but is never the control.

ConcernApproach
Password storagebcrypt through DelegatingPasswordEncoder, so the algorithm can be upgraded without a migration
SessionHttpOnly, Secure, SameSite=Lax cookie; Spring Session JDBC; rotated on login, invalidated on logout and on password change
CSRFEnabled for all cookie-authenticated state-changing requests, cookie-to-header token pattern
Account enumerationLogin and password reset return identical responses and timing whether or not the account exists
ThrottlingPer-username and per-IP limits on login, registration, password reset, and enquiry submission; temporary lockout after repeated failures
IDOREvery customer-scoped query filters by the authenticated user id in the repository method itself, not in a controller check
Mass assignmentExplicit request DTOs; entities are never bound from request bodies
File uploadAllow-list of MIME type and extension, magic-byte signature check, maximum bytes, maximum pixel dimensions, server-generated UUID filenames, stored outside the web root and served as static content only
SpamHoneypot field plus rate limiting on the contact form; CAPTCHA left as an optional extension
Settings contentTyped validation per setting and HTML sanitisation on any rich text, so configurable copy cannot inject script
Error responsesRFC 7807 problem documents; stack traces and SQL never reach the client
ActuatorOnly health, with liveness and readiness groups; everything else disabled in production
SecretsEnvironment variables only; .env and *.pem are gitignored, and logs redact tokens and personal data

A note on the photographs

All ten images carry a small four-point sparkle mark in the lower-right corner, most visible against the darker backdrops. Before these go live as product photography that corner should be cropped or retouched — the pipeline can crop a fixed margin, but it is worth your eye on it first.

Originals stay untouched in assets/originals/. Derivatives are generated at 480, 800, 1280, and 1920 wide in WebP and AVIF with a JPEG fallback, served through srcset with lazy loading below the fold.

Definition of done

Phase one is finished when every one of these works end to end against the Docker Compose stack — not in isolation, and not with a mocked step in the middle.

  • A visitor browses the seeded catalogue, adds to a cart, contacts the business, and places a guest order with an offline payment method.
  • A visitor registers, logs in, changes and resets a password, manages profile and addresses, keeps a server cart, orders, and sees only their own history.
  • The server independently validates prices and stock, and concurrent checkouts cannot oversell.
  • An administrator logs in, is forced to change the seeded password, manages products and photographs, updates prices and stock, and works orders and enquiries.
  • Offline payments are recorded against orders, and cancelling restocks exactly once.
  • Orders survive SMTP being unavailable, and the outbox reports what failed.
  • WhatsApp links open with the configured number and a correctly encoded contextual message.
  • The stack runs through Docker Compose with database and uploads persisting across a restart.
  • Builds, migrations, and the automated test suites pass, with results reported verbatim.
  • No secrets are committed, and no fabricated business claim appears anywhere in the UI.
